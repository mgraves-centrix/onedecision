# Database: moving off SQLite

**Status: implemented and tested, not deployed.**

PostgreSQL is the deployment target. SQLite remains as an explicitly-labeled
zero-setup demo backend so a hackathon judge can run the product from a fresh
clone with no server and no credentials. Both are real, both run the same
migrations, and **the entire test suite runs against both** — 282 runs, 141 per
backend — so they cannot drift without CI going red.

Switching is one environment variable:

```bash
ONEDECISION_DATABASE_URL=postgresql://user:password@host:5432/onedecision
```

Unset it and the app falls back to SQLite. `DATABASE_URL` is also honored, since
most managed platforms inject that name.

---

## Why this was the right next piece of work

`docs/deployment-agentcore.md` named it as the one genuine gap between the demo
and production: *"The demo uses local SQLite, which does not survive a stateless
runtime."* AgentCore Runtime is stateless and horizontally scaled. A file-backed
database in that setting is not slow — it is **wrong**: each instance would hold
its own private copy of the policy set and the audit log.

The interesting part was never "put the tables somewhere else". It was that
three pieces of this system were only correct because SQLite has exactly one
writer.

---

## The three concurrency bugs this surfaced

Each was latent under SQLite and would have been live the moment a second worker
existed.

### 1. The audit hash chain could fork

`audit.record()` reads the current head hash and inserts a successor. That is a
read-modify-write. Two concurrent appenders both read head *H* and both insert
an entry claiming *H* as predecessor — the chain forks, and `verify_chain()`
would report the log intact while an entry had silently been orphaned.

**Fix, in two layers:**

```sql
SELECT pg_advisory_xact_lock(<audit chain key>);   -- serialize appenders
```
```sql
prev_hash TEXT NOT NULL UNIQUE                     -- backstop: a fork cannot commit
```

The lock makes concurrent appends *work*. The constraint makes a fork
*impossible* even if some future code path reaches the insert without the lock.

This is not theoretical. Removing the advisory lock and running
`test_concurrent_audit_appends_keep_the_chain_intact` fails immediately:

```
IntegrityError: duplicate key value violates unique constraint "audit_log_prev_hash_key"
DETAIL:  Key (prev_hash)=(161f71ea4588...) already exists.
```

Eight threads, one contended head, the constraint catching the loser. Restore
the lock and it passes. The test is in `tests/test_database_backends.py`.

### 2. Event de-duplication was select-then-insert

```python
existing = SELECT ... WHERE event_key = ?      # both workers see nothing
if existing: return duplicate
INSERT ...                                      # one succeeds, one crashes
```

Two copies of the same warehouse event would both pass the check; one would then
die on the unique index and surface as an error rather than as the no-op a
duplicate event is supposed to be.

**Fix:** let the database decide the race.

```sql
INSERT INTO exceptions (...) VALUES (...)
ON CONFLICT (event_key) DO NOTHING
RETURNING exception_id
```

No row returned means someone else won; the loser reports a duplicate.
`test_concurrent_duplicate_events_act_once` fires the same event on six threads
and asserts exactly one exception and exactly one work order.

### 3. Money was floating point

`REAL` for a column that gates authorized spending is a latent rounding bug in a
system whose entire point is a spend cap. PostgreSQL uses `NUMERIC(12,2)`,
coerced to `float` at the adapter boundary so no `Decimal` leaks into the domain
or the policy engine (`test_money_never_arrives_as_decimal`).

## What the PostgreSQL schema uses that SQLite cannot express

| Concern | SQLite (demo) | PostgreSQL (target) |
| --- | --- | --- |
| Money | `REAL` | `NUMERIC(12,2)` |
| Flags | `INTEGER` 0/1 | `BOOLEAN` |
| Audit sequence | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` |
| Append-only | `RAISE(ABORT)` triggers | PL/pgSQL trigger + `REVOKE UPDATE, DELETE, TRUNCATE` |
| Chain integrity | `UNIQUE(prev_hash)` | `UNIQUE(prev_hash)` + advisory lock |
| Appender serialization | the file lock | `pg_advisory_xact_lock` |
| Connections | one per call | pooled (`psycopg_pool`) |
| Operational timestamps | — | `recorded_at TIMESTAMPTZ DEFAULT now()` |

`audit_log.created_at` stays a **string on both backends**, deliberately: it is
part of the hashed entry content, so storing it as `TIMESTAMPTZ` and letting the
driver re-render it on read would break `verify_chain()`. `recorded_at` is the
separate operational timestamp for querying and retention.

### Append-only as a privilege, not just a trigger

The migration ends with:

```sql
REVOKE UPDATE, DELETE, TRUNCATE ON audit_log FROM PUBLIC;
```

A trigger stops the application from rewriting history. The revoke stops any
role that is not the table owner from doing so at all. **In a real deployment
the application must connect as a non-owner role** — see *Production hardening*
below. That turns "append-only" from something the code promises into something
the database enforces against the code.

## How it is put together

```
app/db/
  __init__.py               public API: session(), read_only(), init_db(), drop_all()
  base.py                   Connection/Cursor protocols, `?`->`%s`, statement splitter
  sqlite_backend.py         demo backend
  postgres_backend.py       deployment backend: pool, advisory lock, NUMERIC
  migrations/
    0001_baseline.sqlite.sql
    0001_baseline.postgres.sql
```

Application code never imports a driver. It writes ANSI SQL with `?`
placeholders and reads rows as mappings; the backend adapts. The one constraint
this puts on application SQL is that `?` and `%` are reserved — both are handled
by `to_pyformat()`, which skips quoted literals.

### Migrations

Plain SQL, one file per version per dialect, applied in order inside a
transaction and recorded in `schema_migrations`. A failed migration leaves
nothing half-applied. `make migrate` applies anything outstanding.

No ORM and no Alembic: there is no SQLAlchemy in this project to hang Alembic
off, and 11 tables of explicit DDL is more legible than a generated migration
chain. If the schema grows past roughly twice this size, revisit that.

## Running it

```bash
make db-up          # docker compose PostgreSQL + migrations + seed
make test-pg        # the whole suite against BOTH backends
make db-shell       # psql
make db-down
```

Or point at any PostgreSQL:

```bash
export ONEDECISION_DATABASE_URL=postgresql://user:pass@host:5432/onedecision
make migrate && make seed && make run
```

| Variable | Default | Purpose |
| --- | --- | --- |
| `ONEDECISION_DATABASE_URL` | *(unset)* | PostgreSQL DSN. Unset selects SQLite. |
| `DATABASE_URL` | *(unset)* | Honored as the platform convention. |
| `ONEDECISION_DB_POOL_MIN` | `1` | Pool floor. |
| `ONEDECISION_DB_POOL_MAX` | `10` | Pool ceiling. Keep small behind a proxy. |
| `ONEDECISION_DB_CONNECT_TIMEOUT` | `10` | Seconds. |
| `ONEDECISION_TEST_DATABASE_URL` | *(unset)* | Enables the PostgreSQL half of the suite. |

`db.describe()` redacts the password before it reaches a log or the health
endpoint; `test_backend_is_reported_and_never_leaks_the_password` asserts it.

## Production hardening — not yet done

Everything above is implemented and tested against a real PostgreSQL 16. The
following is what still stands between this and a production deployment, in
priority order. None of it is faked in the repository.

1. **Run as a non-owner role.** The `REVOKE` only bites when the application is
   not the table owner. Create `onedecision_app` with `SELECT, INSERT` on
   `audit_log` and full DML elsewhere; run migrations as a separate owner role.
   This is the single highest-value remaining change, because it makes the
   audit log tamper-proof against the application itself.
2. **Secrets from a secret manager.** The DSN is read from the environment today.
   In AWS it should come from Secrets Manager or SSM Parameter Store, with
   rotation, and IAM database authentication instead of a password where
   possible.
3. **TLS.** Require it: append `?sslmode=verify-full&sslrootcert=...`. The code
   passes the DSN through untouched, so this is configuration, not a change.
4. **Connection management for a serverless runtime.** AgentCore Runtime scales
   horizontally, and *N* instances × `pool_max` can exhaust a database's
   connection limit. Put RDS Proxy (or PgBouncer in transaction mode) in front
   and set `ONEDECISION_DB_POOL_MAX` to 2–5. Note that transaction-mode pooling
   forbids session-scoped state — this codebase uses only
   `pg_advisory_xact_lock`, which is transaction-scoped and therefore safe. A
   future `pg_advisory_lock` (session-scoped) would silently break under it.
5. **Sizing.** Aurora Serverless v2 or a small RDS instance. The workload is
   tiny and bursty; the audit log is the only table that grows without bound.
6. **Retention.** `audit_log` is append-only and never pruned. Partition it by
   `recorded_at` monthly and archive cold partitions to S3. Do not add a delete
   path — that is the property the table exists to provide.
7. **Backups and PITR.** Automated backups with point-in-time recovery. The
   hash chain makes tampering *detectable*; backups make it *recoverable*.
8. **`JSONB` for payloads.** `audit_log.payload`, `policies.definition`, and
   `decision_cards.payload` are `TEXT` holding JSON, so both backends share one
   code path. Moving them to `JSONB` with GIN indexes would allow querying the
   audit log by payload contents. It diverges the read path, so it needs its own
   migration and its own tests.
9. **`TIMESTAMPTZ` for operational timestamps.** Every timestamp outside the
   audit chain is an ISO-8601 string. Converting them is mechanical but touches
   template rendering and the `PolicyRecord` dataclass.
10. **Read replicas.** Only if the replay evaluator over a large historical set
    becomes hot. It is currently milliseconds.

## What is claimed

**Claimed:** the application runs unmodified on PostgreSQL 16; the full suite
passes on both backends; three concurrency defects found and fixed with tests
that fail when the fix is removed; migrations, pooling, password redaction, and
database-enforced append-only semantics.

**Not claimed:** any cloud deployment, RDS or Aurora provisioning, a non-owner
role, TLS verification against a real endpoint, or load testing.
